# 脚手架不足与改进点

本文档记录当前脚手架中已识别的问题和可改进方向，供后续迭代参考。

---

## 1. Provider 未传 tool definitions

**位置**：`agent/loop.py` → `run_once()`

**问题**：`AgentLoop.run_once()` 调用 `provider.chat()` 时，没有将 `ToolRegistry` 中注册的工具定义传给 LLM。这意味着 LLM 不知道当前有哪些工具可用，无法发起工具调用。

**现状**：
```python
# loop.py:105
response = await self.provider.chat_with_retry(
    messages=session.messages,
    model=self.config.get("agents", {}).get("model"),
)
```

**期望**：
```python
response = await self.provider.chat_with_retry(
    messages=session.messages,
    model=self.config.get("agents", {}).get("model"),
    tools=self.tools.get_definitions(),  # ← 缺少这一步
)
```

---

## 2. chat() 签名不支持 tools 参数

**位置**：`providers/base.py` → `LLMProvider.chat()`

**问题**：`LLMProvider.chat()` 的抽象方法签名只有 `messages / model / max_tokens / temperature` 四个参数，缺少 `tools` 参数。即使 `run_once()` 传入了工具定义，Provider 也无法接收。

**影响范围**：所有 Provider 子类（`DemoProvider`、`OpenAIProvider`、`AnthropicProvider`）都需要同步修改签名。

**改进方向**：
- 在 `LLMProvider.chat()` 签名中增加 `tools: list[dict] | None = None` 参数
- 各子类实现中将 tools 透传给对应的 API 调用
- `DemoProvider` 需要模拟工具调用的返回逻辑

---

## 3. 配置系统未打通

**位置**：`config/schema.py` vs `agent/loop.py` / `facade.py`

**问题**：`config/schema.py` 定义了完整的 Pydantic 配置模型（`AppConfig`、`AgentConfig`、`ProviderConfig`），但 `AgentLoop.from_config()` 和 `Nanobot.from_config()` 接受的是原始 `dict`，两者没有连接。

**现状**：
```python
# facade.py — 传入的是 dict
bot = Nanobot.from_config({"provider": "demo", "model": "demo-model"})

# config/schema.py — 定义了结构化模型但未被使用
class AppConfig(BaseModel):
    agents: AgentConfig = Field(default_factory=AgentConfig)
    channels: dict[str, Any] = Field(default_factory=dict)
```

**改进方向**：
- `Nanobot.from_config()` 接受 `AppConfig | dict | None`
- 内部统一用 `AppConfig` 校验和传递配置
- `config/loader.py` 的 `load_config()` 结果直接接入 Facade

---

## 4. Session 无持久化

**位置**：`session/manager.py`

**问题**：`SessionManager` 纯内存存储，进程退出后所有会话历史丢失。对于需要跨会话保持上下文的场景（如 CLI 长期运行、多轮对话）不适用。

**改进方向**：
- 定义 `SessionStore` 抽象接口（`save` / `load` / `delete`）
- 提供内置实现：`MemorySessionStore`（当前行为）、`FileSessionStore`（JSON/SQLite）
- `SessionManager` 通过注入 `SessionStore` 切换存储后端

---

## 5. ChannelManager 未被使用

**位置**：`channels/manager.py` vs `cli.py`

**问题**：`ChannelManager` 实现了完整的渠道生命周期管理（自动发现、启停、出站消息路由、重试），但 `cli.py` 的三种运行模式都没有使用它：

- `demo` 模式：直接调用 `Nanobot.from_config()`，绕过消息总线
- `chat` 模式：手动组装 `AgentLoop` + `EventBus`，手动读取 stdin
- `sdk` 模式：直接调用 Facade

**改进方向**：
- `chat` 模式应改为：`ChannelManager` + `CliChannel` + `AgentLoop` 的标准组装
- 提供一个 `gateway` 运行模式，展示完整的 Channel → Bus → Agent 流程

---

## 6. httpx 依赖未使用

**位置**：`pyproject.toml` vs 各 Provider 实现

**问题**：`pyproject.toml` 声明了 `httpx>=0.27.0` 依赖，但三个 Provider 实现都没有使用它：
- `DemoProvider` — 纯本地模拟，不需要 HTTP
- `OpenAIProvider` — 使用 `openai` SDK 内置的 HTTP 客户端
- `AnthropicProvider` — 使用 `anthropic` SDK 内置的 HTTP 客户端

**改进方向**：
- 如果 httpx 是为未来扩展预留的，在 README 中说明
- 如果不需要，从依赖中移除，减小安装体积
- 或者用 httpx 实现一个通用的 HTTP Provider（不依赖 openai/anthropic SDK）

---

## 7. 缺少 System Prompt 支持

**位置**：`agent/loop.py` → `run_once()`

**问题**：`run_once()` 没有机制注入系统提示词（system prompt）。LLM 的行为引导完全依赖用户消息，无法在会话级别设定角色、规则等。

**改进方向**：
- 在 `config` 中增加 `system_prompt` 字段
- `run_once()` 开始时自动注入 system message
- `Session.add_message()` 已支持 `role="system"`，只需在循环初始化时调用

---

## 8. DemoProvider 的工具调用模拟缺失

**位置**：`providers/demo_provider.py`

**问题**：`DemoProvider` 只返回固定文本响应，不模拟工具调用（`tool_calls`）。这导致 `AgentLoop` 中的工具执行分支（`response.has_tool_calls`）在 demo 模式下永远不会被触发，无法完整演示 Agent 循环。

**改进方向**：
- 对特定关键词（如 "tools"、"echo"、"add"）返回模拟的 `tool_calls`
- 让 demo 模式能完整走通：用户消息 → LLM 决策 → 工具执行 → 结果回传 → 最终响应

---

## 9. 错误处理不够细化

**位置**：`providers/base.py` → `_is_transient_error()`

**问题**：瞬态错误判断基于字符串匹配（`"429"`, `"rate limit"`, `"500"` 等），这种方式：
- 容易误判（如用户消息中包含 "500" 这个数字）
- 无法区分 HTTP 状态码和响应体中的文本
- 不同 Provider 的错误格式不同，统一匹配不精确

**改进方向**：
- 在 `LLMResponse` 中增加 `status_code` 字段
- `_is_transient_error()` 优先检查 status_code，其次检查文本
- 各 Provider 子类可以在 `chat()` 中设置精确的错误分类

---

## 10. 缺少并发安全机制

**位置**：`session/manager.py`、`agent/tools/registry.py`

**问题**：`SessionManager` 和 `ToolRegistry` 的内部字典没有并发保护。在多 Channel 同时向同一 session 发消息的场景下，可能出现竞态条件。

**改进方向**：
- 为 `Session` 的消息列表加 `asyncio.Lock`
- 或在 `AgentLoop.process_message()` 层面用 session_key 做串行化
- `ToolRegistry` 通常是启动时注册、运行时只读，风险较低，可暂不处理

---

## 改进优先级建议

| 优先级 | 编号 | 原因 |
|--------|------|------|
| P0（阻塞核心功能） | #1, #2 | 没有 tool definitions 传递，Agent 循环的工具调用分支完全不可用 |
| P1（影响可用性） | #3, #7, #8 | 配置打通、system prompt、demo 工具调用是实际使用的前提 |
| P2（架构完善） | #4, #5, #9 | 持久化、ChannelManager 集成、错误处理细化 |
| P3（锦上添花） | #6, #10 | 依赖清理、并发安全 |
